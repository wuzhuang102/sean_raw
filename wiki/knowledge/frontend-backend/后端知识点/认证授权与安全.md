# 定位

认证、授权与安全是后端系统的边界控制层。它不是登录页上的一个功能，而是贯穿请求入口、会话、权限判断、数据访问、审计、密钥、异常处理和运维响应的一组工程约束。

最重要的三句话：

- 认证 Authentication：确认“请求者是谁”。
- 授权 Authorization：确认“这个请求者能不能对这个资源做这个动作”。
- 安全 Security：在认证和授权之外，继续限制输入、输出、依赖、密钥、文件、网络和运行环境的风险。

一个典型请求的安全链路：

1. 请求进入网关或应用。
2. 校验 TLS、来源、限流和基础格式。
3. 解析 Session、Cookie、Bearer Token、API Key 或 mTLS 身份。
4. 得到主体：user、service account、tenant、organization、role、scope、device、risk signal。
5. 按资源、动作和上下文做权限判断。
6. 执行业务逻辑前做输入校验和业务不变量校验。
7. 数据库查询必须按租户、所有者和权限范围收敛。
8. 记录审计日志、异常、指标和安全事件。

# 基础概念

## Principal

Principal 是被认证出来的主体，可以是用户、内部服务、API 调用方、后台任务、机器人账号或第三方应用。

示例：

```json
{
  "principal_type": "user",
  "user_id": "u_123",
  "tenant_id": "t_456",
  "roles": ["workspace_admin"],
  "scopes": ["project:read", "project:write"],
  "auth_method": "password+mfa"
}
```

后端不要只传一个 `user_id` 就认为安全上下文完整。实际工程里常常还需要 tenant、账号状态、登录方式、权限版本、会话 id、设备信息和风险标记。

## Credential、Authenticator、Token

- Credential：用于证明身份的材料，例如密码、私钥、客户端密钥、一次性验证码。
- Authenticator：产生或持有认证证明的东西，例如密码管理器、TOTP App、Passkey、安全密钥。
- Token：认证完成后用于后续请求的临时凭证，例如 Session ID、JWT access token、opaque access token、refresh token。

常见错误是把 token 当成永久身份。token 只是临时通行证，要有过期、撤销、轮换和泄漏后的处理策略。

## 401 与 403

- 401 Unauthorized：未认证、认证失败或凭证过期。实际含义更接近“你还没通过身份验证”。
- 403 Forbidden：已经知道你是谁，但你没有权限。

示例：

```http
GET /api/admin/users
Authorization: Bearer expired_token

HTTP/1.1 401 Unauthorized
```

```http
GET /api/admin/users
Authorization: Bearer valid_non_admin_token

HTTP/1.1 403 Forbidden
```

对敏感资源，有时为了避免泄漏资源是否存在，会把无权访问的资源统一返回 404。这是产品和安全共同决定的策略，不应由单个接口随意处理。

# 认证方式

## Session + Cookie

Session + Cookie 是传统 Web 应用最常见、仍然很实用的认证方案。

流程：

1. 用户提交账号密码。
2. 服务端校验成功后创建 session 记录。
3. 服务端返回 `Set-Cookie: sid=...`。
4. 浏览器后续自动带上 Cookie。
5. 服务端根据 session id 查询登录状态。

适合场景：

- 服务端渲染或同域 Web 应用。
- 需要强撤销能力，例如后台管理、金融、企业内部系统。
- 服务端可以维护 session store，例如 Redis、数据库或内存集群。

关键实践：

- Cookie 设置 `HttpOnly`，避免被 JavaScript 直接读取。
- Cookie 设置 `Secure`，只允许 HTTPS 传输。
- 根据业务设置 `SameSite=Lax` 或 `Strict`，跨站嵌入或第三方登录场景再谨慎使用 `None; Secure`。
- 登录成功、权限提升、绑定 MFA 后轮换 session id，降低 session fixation 风险。
- 设置 idle timeout 和 absolute timeout。
- 登出、改密、账号冻结时能撤销 session。

示例：

```http
Set-Cookie: sid=s_abc; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=7200
```

常见误区：

- 把 session id 放 URL query，容易被日志、Referer、截图和浏览器历史泄漏。
- 只做前端路由拦截，不在后端验证 session。
- session 永不过期，账号风险事件后不强制重新认证。

## JWT

JWT 是一种自包含 token 格式，常用于 API、移动端、前后端分离和服务间传递身份声明。

JWT 常见结构：

```json
{
  "sub": "u_123",
  "iss": "https://auth.example.com",
  "aud": "api.example.com",
  "exp": 1781064000,
  "iat": 1781060400,
  "tenant_id": "t_456",
  "scope": "project:read project:write"
}
```

适合场景：

- 多个服务需要无状态校验 access token。
- API 网关或资源服务只需要验证签名和少量声明。
- 与 OAuth/OIDC 身份提供方集成。

关键实践：

- 必须校验签名、过期时间、issuer、audience 和算法。
- access token 短有效期；refresh token 单独保护、轮换和撤销。
- 不要在 JWT 中放密码、身份证、手机号、商业敏感字段等不必要信息。
- 不要把 JWT 当数据库状态替代品；权限、账号状态和租户关系变化可能需要服务端二次查询或 token 版本失效机制。
- 明确密钥轮换方案，使用 `kid` 标识签名密钥。

常见误区：

- 只 base64 decode，不校验签名。
- 接受 `alg=none` 或算法混淆。
- JWT 有效期设置成几天甚至几个月。
- 以为 JWT “无状态”就天然支持登出和封号；实际上撤销需要 blocklist、token version、短 TTL 或回查。

## OAuth 2.0 与 OpenID Connect

OAuth 2.0 主要解决授权委托：用户允许第三方应用访问某些资源。OpenID Connect 在 OAuth 2.0 之上增加身份认证层，用 ID Token 表达“用户是谁”。

简单区分：

- OAuth 2.0：能不能访问资源，核心是 access token 和 scope。
- OpenID Connect：用户身份是什么，核心是 ID Token、subject、issuer。

常见角色：

- Resource Owner：资源拥有者，通常是用户。
- Client：发起授权的应用。
- Authorization Server：认证和发 token 的服务。
- Resource Server：持有 API 资源的服务。

后端 Web 应用常用授权码流程：

1. 用户访问应用。
2. 应用把用户重定向到授权服务器。
3. 用户登录并同意授权。
4. 授权服务器带 authorization code 回调应用。
5. 应用后端用 code 换 token。
6. 应用用 access token 调资源 API；如需登录态，用 ID Token 建立本地用户会话。

关键实践：

- 新应用优先使用 Authorization Code + PKCE。
- redirect URI 精确匹配，不要用宽泛通配。
- 使用 `state` 防 CSRF，使用 `nonce` 绑定 OIDC 登录请求。
- 不再使用 implicit flow 作为现代默认方案。
- access token 只给资源服务器使用；前端不应把 ID Token 当 API 访问凭证。
- scope 只表达授权范围，不等价于业务权限模型。

适合场景：

- 第三方登录：用 OIDC 登录 Google、GitHub、企业 IdP。
- 开放平台：用户授权第三方应用读取自己的数据。
- 企业 SSO：统一身份提供方管理账号、MFA 和登录策略。

常见误区：

- “接了 OAuth 就完成权限系统”：OAuth 只解决授权委托，业务里的项目、订单、租户、角色仍要自己判断。
- 混淆 access token 与 ID Token。
- 回调接口不校验 state，导致登录 CSRF 或账号绑定错误。

## OAuth/OIDC 与 CAS 对比

CAS 通常指 Central Authentication Service，是企业和学校场景里常见的 Web 单点登录体系。它和 OAuth/OIDC 都可能出现在“统一登录”方案里，但解决问题的抽象不同。

一句话区分：

- CAS：偏“Web 单点登录协议”，重点是用户登录一次后访问多个受信任 Web 应用。
- OAuth 2.0：偏“授权委托协议”，重点是第三方或客户端能否代表用户访问资源。
- OpenID Connect：在 OAuth 2.0 之上补身份层，重点是标准化表达“用户是谁”。

典型 CAS 登录流程：

1. 用户访问业务系统 A。
2. A 发现用户未登录，把用户重定向到 CAS Server，并带上 `service` 回跳地址。
3. 用户在 CAS Server 登录。
4. CAS Server 生成 service ticket，把用户重定向回业务系统 A。
5. A 拿 ticket 到 CAS Server 校验。
6. 校验成功后，A 建立自己的本地登录态。
7. 用户再访问业务系统 B 时，CAS Server 通过单点登录状态直接给 B 发新的 service ticket。

OAuth/OIDC 常见登录流程则是：

1. 应用把用户重定向到 Authorization Server。
2. 用户登录并授权。
3. 应用拿 authorization code。
4. 后端用 code 换 token。
5. 应用用 ID Token 建立登录态，用 access token 访问资源 API。

核心差异：

| 维度 | CAS | OAuth 2.0 | OpenID Connect |
| --- | --- | --- | --- |
| 主要目标 | Web SSO | 授权委托 | 身份认证 + 登录 |
| 典型凭证 | TGT、ST、service ticket | authorization code、access token、refresh token | ID Token、access token |
| 用户信息表达 | CAS 校验响应里的 principal/attributes | 协议本身不定义登录身份 | 标准化 claims，例如 `sub`、`iss`、`aud` |
| 资源访问 | 不是重点，通常各业务系统本地处理 | 核心能力，按 scope 访问资源 API | 可配合 access token 访问资源 |
| 适合系统 | 组织内部 Web 应用、校园/企业 SSO、遗留系统整合 | 开放平台、第三方授权、API 访问 | 第三方登录、企业 IdP、现代 Web/移动登录 |
| 生态 | Java/企业内网/老系统常见 | API、移动端、开放平台广泛 | 云身份、SaaS、现代 IdP 广泛 |

后端选型时可以这样判断：

- 如果只是组织内部多个 Web 系统统一登录，且已有 CAS Server 或历史系统依赖 CAS，CAS 是合理方案。
- 如果要做“用 Google/GitHub/企业 IdP 登录”，优先看 OIDC。
- 如果要让第三方应用访问用户数据，例如读取日历、仓库、文件，应该用 OAuth 2.0 授权模型。
- 如果前后端分离、移动端、开放 API、微服务资源服务器很多，OIDC/OAuth 生态通常更通用。
- 如果只是自己系统内部登录，不需要第三方授权或统一身份平台，Session + Cookie 可能更简单。

常见混淆：

- 把 CAS 当成 OAuth：CAS 的 service ticket 不是 access token，不适合直接拿来做开放 API 授权。
- 把 OAuth 当成登录：OAuth 2.0 本身不标准化用户身份；要登录应使用 OIDC 或 IdP 提供的明确身份接口。
- 把 SSO 当成权限系统：无论 CAS 还是 OIDC，都只解决“统一认证/登录”的一部分，业务权限、租户隔离、资源级授权仍要在业务系统里做。
- 认为接入 CAS/OIDC 后本地不需要 session：多数 Web 应用仍会在本系统里建立本地登录态，并维护用户映射、权限和审计。

## API Key

API Key 常用于服务调用、开放平台、Webhook 和机器身份。

适合场景：

- 服务端到服务端调用。
- 第三方开发者调用开放 API。
- 内部脚本、CI、自动化任务调用。

关键实践：

- key 只展示一次，服务端只存 hash 或可验证摘要。
- key 带前缀便于识别，例如 `sk_live_xxx`、`whsec_xxx`。
- 支持创建、禁用、轮换、过期和按权限 scope 限制。
- 每个 key 绑定 owner、tenant、用途、环境和最后使用时间。
- 日志、错误、监控里必须脱敏。

示例：

```http
GET /v1/projects
Authorization: Bearer sk_live_xxx
```

常见误区：

- 所有客户共用一个 key。
- key 永不过期、无法撤销。
- 把 key 放前端代码、移动端包或公开仓库。
- key 泄漏后无法定位是谁、何时、从哪里调用。

## mTLS 与服务间身份

mTLS 用客户端证书证明调用方身份，常用于服务网格、内部微服务、高安全接口和企业集成。

适合场景：

- 内部服务之间需要强身份。
- 零信任网络中不再默认信任内网 IP。
- 与合作方进行高安全双向认证。

关键实践：

- 证书生命周期要自动化：签发、分发、轮换、吊销。
- 服务身份应绑定 workload，而不是绑定机器名或 IP。
- mTLS 解决“谁连过来”，不自动解决“它能做什么”；仍需授权策略。

# 密码与账号安全

## 密码存储

密码绝不能明文存储，也不应使用普通快速 hash，例如 MD5、SHA-1、SHA-256 直接 hash。

推荐思路：

- 使用专门的密码哈希算法：Argon2id、bcrypt、scrypt、PBKDF2。
- 每个密码使用独立随机 salt。
- 设置成本参数，让离线爆破变贵。
- 可选使用 pepper，但 pepper 要放在独立密钥管理系统，不要和数据库放一起。

示例字段：

```text
password_hash = "$argon2id$v=19$m=65536,t=3,p=4$..."
password_updated_at = "2026-06-10T03:00:00Z"
```

不要自己设计密码学方案。工程重点是选成熟库、设置合理参数、支持参数升级和迁移旧 hash。

## 密码策略

现代密码策略更强调长度、泄漏检测和 MFA，而不是强制复杂字符组合。

建议：

- 允许长密码和空格。
- 不静默截断密码。
- 阻止常见弱密码和已泄漏密码。
- 提供密码强度提示。
- 不做无原因的周期性强制改密；发现泄漏、风险事件或认证器变化时再触发。
- 高风险账号启用 MFA。

常见误区：

- 要求“8 位，必须大小写数字特殊字符”，但允许 `Password1!`。
- 限制最大长度过短，反而阻碍密码管理器和 passphrase。
- 忘记登录失败限流，导致撞库和爆破成本很低。

## MFA、Passkey 与风险认证

MFA 是多因素认证，常见因素包括：

- 知识：密码、PIN。
- 持有：手机、TOTP、安全密钥。
- 生物特征：指纹、人脸，通常由设备本地完成验证。

常见 MFA：

- TOTP：Google Authenticator、1Password 等生成一次性码。
- WebAuthn/Passkey：抗钓鱼能力更强，体验也更好。
- 短信验证码：比没有强，但容易受 SIM swap、短信劫持和运营商风险影响，不应作为高安全场景首选。

风险认证触发点：

- 新设备、新地区、异常 IP。
- 密码重置、邮箱变更、绑定新 MFA。
- 提现、转账、删除关键资源、导出数据。
- 管理员权限提升。

# 授权模型

## RBAC

RBAC 按角色授权。用户拥有角色，角色拥有权限。

适合场景：

- 后台管理系统。
- 企业 SaaS 中角色比较稳定。
- 权限可以归纳为管理员、编辑者、查看者等。

示例：

```text
role: workspace_admin
permissions:
  - project:create
  - project:read
  - project:update
  - member:invite
```

优点：

- 容易理解和管理。
- UI 展示简单。
- 适合多数中小系统起步。

风险：

- 角色膨胀：每个客户都要一个特殊角色。
- 只检查角色，不检查资源归属。
- 角色名写死在代码里，后期迁移困难。

## ABAC

ABAC 按属性和上下文授权。判断时使用主体属性、资源属性、动作和环境。

示例：

```text
允许 user 读取 document，当：
- user.tenant_id == document.tenant_id
- document.status == "published" 或 user.department == document.department
- request.ip 在公司网络内
```

适合场景：

- 多租户、跨组织、跨部门权限。
- 数据权限依赖资源状态、地域、时间、设备、风控评分。
- 角色无法覆盖所有条件。

优点：

- 表达能力强。
- 适合细粒度权限。

风险：

- 策略复杂后难以调试。
- 如果没有测试和审计，容易出现隐性越权。

## ACL

ACL 直接记录某个主体对某个资源的权限。

示例：

```text
resource: document_123
acl:
  - user:u_1 -> read
  - user:u_2 -> read,write
  - group:g_1 -> read
```

适合场景：

- 文档协作。
- 云盘、项目、看板、代码仓库。
- 用户可以把资源分享给具体人或组。

风险：

- 数据量大时查询和继承复杂。
- 分享链路、撤销、组成员变化需要严格处理。

## 多租户隔离

多租户系统里，tenant、workspace、organization、project 常常比 role 更重要。很多严重越权不是因为角色错，而是查询没带租户边界。

危险代码：

```sql
SELECT * FROM orders WHERE id = $1;
```

更安全的形态：

```sql
SELECT * FROM orders
WHERE id = $1 AND tenant_id = $2;
```

工程实践：

- 所有核心表带 `tenant_id` 或明确的归属链路。
- Repository 层默认接收 auth context，不允许自由拼无租户查询。
- 管理员跨租户操作必须有显式 break-glass 审计。
- 列表、详情、更新、删除都要做租户边界，不只列表做。

# 权限判断的工程落地

## 权限判断放哪里

常见层次：

- 网关层：校验 token、基础 scope、限流、WAF。
- Middleware：解析身份、注入 auth context。
- Handler：检查动作级权限，例如 `project:create`。
- Service/Domain：检查业务状态权限，例如只有 owner 可转移项目。
- Repository/SQL：收敛数据边界，例如 tenant_id、owner_id。

不要把所有权限都塞在一个地方。认证可以集中，授权要靠近资源和业务规则。

## 权限函数示例

```ts
type AuthContext = {
  userId: string;
  tenantId: string;
  roles: string[];
  permissions: string[];
};

function canUpdateProject(ctx: AuthContext, project: { tenantId: string; ownerId: string }) {
  if (ctx.tenantId !== project.tenantId) return false;
  if (ctx.permissions.includes("project:update:any")) return true;
  if (ctx.permissions.includes("project:update:own") && project.ownerId === ctx.userId) return true;
  return false;
}
```

要点：

- 先判断租户边界，再判断角色或权限。
- 权限函数返回布尔值或结构化拒绝原因，不要散落在 Controller 里。
- 为每类敏感动作写反向测试：无权限用户、跨租户用户、普通成员、资源所有者、管理员。

## IDOR

IDOR 是 Insecure Direct Object Reference：用户通过猜测或替换资源 id 访问不属于自己的资源。

危险示例：

```http
GET /api/invoices/inv_10086
```

如果后端只按 `invoice_id` 查询，不校验当前用户或租户是否有权访问，就会产生横向越权。

防护：

- 每次按 id 查询资源后都校验归属和权限。
- SQL 中带上 tenant/user 条件。
- 不依赖“id 很难猜”作为主要防线。
- 对导出、下载、预签名 URL、批量接口也做同样检查。

# 常见 Web 与 API 安全风险

## SQL 注入

原因：把用户输入拼进 SQL 字符串。

危险示例：

```ts
db.query(`SELECT * FROM users WHERE email = '${email}'`);
```

安全做法：

```ts
db.query("SELECT * FROM users WHERE email = ?", [email]);
```

实践：

- 使用参数化查询或成熟 ORM。
- 不把排序字段、表名、列名直接交给用户；这类动态结构要白名单映射。
- 数据库账号最小权限。
- 对错误信息做统一处理，不把 SQL 错误直接返回给用户。

## XSS

XSS 是攻击者让页面执行恶意脚本。后端相关点包括输出编码、富文本清洗、Cookie 安全和 CSP。

场景：

- 用户昵称、评论、工单内容被原样渲染。
- Markdown/HTML 富文本未清洗。
- 后台运营系统展示用户提交内容。

防护：

- 默认使用模板引擎或前端框架的自动转义。
- 富文本使用白名单 sanitizer。
- Cookie 设置 `HttpOnly`，降低 token 被脚本读取的风险。
- 高价值系统配置 Content Security Policy。

## CSRF

CSRF 利用浏览器自动携带 Cookie 的特性，让用户在已登录状态下发起非本意请求。

高风险场景：

- 使用 Cookie 登录态。
- 修改密码、绑定邮箱、转账、删除数据、创建订单等状态变更接口。

防护：

- SameSite Cookie。
- CSRF token。
- 对敏感操作要求重新认证或二次确认。
- 状态变更接口不要使用 GET。
- 校验 Origin/Referer 作为辅助措施。

如果使用 `Authorization: Bearer ...` 且 token 不会被浏览器自动跨站携带，CSRF 风险通常低很多，但仍要关注 XSS 和 token 存储。

## SSRF

SSRF 是服务端根据用户输入去请求攻击者指定的地址，导致内网探测、云元数据泄漏或访问内部管理接口。

危险场景：

- “通过 URL 导入图片/文档”。
- Webhook 测试请求。
- 代理下载、网页截图、PDF 生成。

防护：

- URL host 白名单优先。
- 禁止访问内网 IP、localhost、link-local、云 metadata 地址。
- 解析 DNS 后校验最终 IP，防 DNS rebinding。
- 限制协议，只允许 http/https。
- 设置超时、大小限制、重定向限制。
- 下载内容存储后重新分发，不直接把内部响应透传。

## 命令注入

原因：把用户输入拼到 shell 命令。

危险示例：

```ts
exec(`convert ${filename} output.png`);
```

防护：

- 优先使用库 API，不调用 shell。
- 必须调用外部程序时，使用参数数组，不经过 shell 拼接。
- 输入做白名单校验。
- 运行环境最小权限、隔离工作目录、限制资源。

## 文件上传

文件上传风险包括木马、超大文件、路径穿越、内容伪装、压缩炸弹和公开访问控制错误。

实践：

- 限制大小、类型、数量和上传频率。
- 不信任客户端 MIME；服务端检测 magic bytes。
- 文件名重新生成，不直接使用用户文件名作为路径。
- 上传目录不允许执行脚本。
- 图片等文件重新编码或扫描。
- 私有文件下载必须走鉴权，不把对象存储地址永久公开。

## 敏感信息泄漏

常见泄漏点：

- 日志打印 token、Cookie、密码、API Key、身份证、手机号。
- 错误响应带堆栈、SQL、内部服务地址。
- 前端 bundle 带服务端密钥。
- Git 仓库提交 `.env`。
- 监控、Apm、错误平台采集了敏感字段。

实践：

- 日志字段分级和脱敏。
- secret scanning。
- 错误响应统一包装。
- 配置和密钥走 secret manager 或环境注入。
- 定期轮换密钥，确保泄漏后能快速撤销。

# 安全设计场景

## 场景一：普通 SaaS 登录

推荐组合：

- 邮箱/手机号 + 密码。
- 密码使用 Argon2id/bcrypt 存储。
- 登录失败按账号、IP、设备做限流。
- Session Cookie 或短期 access token。
- 管理员和高风险操作启用 MFA。
- 改密、改邮箱、绑定 MFA 后通知用户并撤销旧 session。

核心表：

```text
users(id, email, password_hash, status, password_updated_at)
sessions(id_hash, user_id, tenant_id, expires_at, last_seen_at, revoked_at)
mfa_authenticators(id, user_id, type, secret_or_public_key, created_at)
login_events(id, user_id, ip, user_agent, result, created_at)
```

## 场景二：企业后台 RBAC

推荐组合：

- 用户属于 organization/workspace。
- 用户绑定 role。
- role 映射 permission。
- 后端每个接口声明需要的 permission。
- 数据查询始终加 tenant/workspace 条件。

示例：

```text
GET /admin/users -> member:read
POST /admin/users -> member:invite
PATCH /projects/:id -> project:update
DELETE /projects/:id -> project:delete
```

测试用例必须覆盖：

- 未登录访问。
- 普通用户访问管理员接口。
- A 租户用户访问 B 租户资源。
- 资源 owner 与非 owner。
- 角色变更后旧 token 是否仍有过期前权限。

## 场景三：开放 API

推荐组合：

- API Key 或 OAuth access token。
- 每个 key 绑定应用、环境、scope、限流策略。
- key 只存 hash。
- 请求带 request id，审计调用方、IP、路径、状态码。
- 支持按 key 禁用、轮换和查看最后使用时间。

示例：

```http
POST /v1/refunds
Authorization: Bearer sk_live_...
Idempotency-Key: refund_20260610_001
```

退款、扣款、创建订单等接口还需要幂等键，安全与一致性要一起设计。

## 场景四：微服务调用

推荐组合：

- 内部服务使用 mTLS 或 workload identity。
- 网关校验外部身份，内部服务仍校验调用方服务身份和权限。
- 服务间 token 使用短 TTL。
- 高风险内部接口做显式 allowlist。

误区：

- 认为“在内网”就不需要鉴权。
- 只校验用户 token，不校验调用方服务是否有权执行该动作。
- 共享一个超级内部 token。

# 审计、监控与响应

应记录的安全事件：

- 登录成功/失败、MFA 失败、账号锁定。
- 密码重置、邮箱变更、绑定/解绑认证器。
- 角色、权限、成员变更。
- API Key 创建、查看、禁用、轮换。
- 敏感数据导出、批量删除、跨租户管理操作。
- 权限拒绝、风控拦截、异常访问频率。

审计日志字段：

```json
{
  "actor_type": "user",
  "actor_id": "u_123",
  "tenant_id": "t_456",
  "action": "project.delete",
  "resource_type": "project",
  "resource_id": "p_789",
  "result": "denied",
  "ip": "203.0.113.10",
  "request_id": "req_abc",
  "created_at": "2026-06-10T03:20:00Z"
}
```

注意：

- 审计日志要防篡改，至少普通业务管理员不能删除。
- 审计日志本身也可能包含敏感信息，需要访问控制。
- 不要为了审计把密码、完整 token、完整 API Key 写进去。

# 最小检查清单

## 认证

- 登录接口全站 HTTPS。
- 密码使用成熟密码哈希算法存储。
- 登录失败有限流和监控。
- 账号枚举风险可控，错误信息不泄漏过多。
- Session/Cookie/JWT 有过期、撤销和轮换策略。
- 高风险操作要求重新认证或 MFA。

## 授权

- 每个非公开接口都有服务端权限判断。
- 租户边界在查询层落实。
- 详情、更新、删除、导出、批量接口都检查资源归属。
- 管理员权限最小化，有审计。
- 权限变更后旧会话或旧 token 的影响可控。
- 有横向越权和纵向越权测试。

## API 与输入

- SQL 使用参数化查询。
- 动态排序、字段选择、过滤条件有白名单。
- 文件上传限制大小、类型、路径和访问权限。
- URL 抓取类功能有 SSRF 防护。
- 错误响应不暴露堆栈、SQL 和内部地址。

## 密钥与运维

- secret 不进 Git，不进前端 bundle，不完整进入日志。
- API Key、JWT signing key、数据库密码可轮换。
- 生产权限按最小权限分配。
- 安全事件有告警和处置路径。

# 常见误区

- “前端隐藏按钮就等于没权限”：权限必须在服务端判断。
- “JWT 无状态所以不用查数据库”：账号冻结、权限变更、租户关系变化仍可能需要回查或版本控制。
- “管理员可以跳过所有检查”：管理员也要受租户、审计和高风险确认约束。
- “内网接口不用鉴权”：内网被打穿、SSRF、配置错误和供应链风险都会让内部接口暴露。
- “密码 hash 了就安全”：弱 hash、无 salt、低成本参数、无登录限流仍然危险。
- “接入 OAuth/OIDC 就完成安全”：它解决身份和授权委托的一部分，不替代业务权限、数据隔离和审计。

# 后续学习顺序

1. 先实现一个 Session + Cookie 登录：注册、登录、登出、改密、session 过期。
2. 给一个多租户资源加 RBAC：workspace、member、role、permission、project。
3. 补横向越权测试：A 用户不能读写 B 用户资源，A 租户不能访问 B 租户。
4. 增加 API Key：创建、hash 存储、scope、禁用、最后使用时间。
5. 接入一个 OIDC 登录：Authorization Code + PKCE、state、nonce、本地账号绑定。
6. 增加审计日志和安全告警：权限变更、导出、删除、登录异常。
