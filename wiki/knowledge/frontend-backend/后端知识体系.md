# 阅读路径

这页是后端知识体系的主入口。推荐阅读顺序：

1. 先建立后端整体地图：请求处理链路、数据持久化、状态、并发、可靠性、安全、部署与观测。
2. 再围绕一个真实 API 项目补课：认证、数据库建模、事务、缓存、队列、日志、错误处理、测试、部署。
3. 最后按问题专题深化：性能瓶颈、数据一致性、分布式系统、云原生、故障排查、架构演进。

相关基础页：[Docker 常用基础语法](Docker基础语法.md)。

# 总体心智模型

后端不是“写几个接口”，而是把业务规则、数据状态、系统边界和运行可靠性放到服务端管理。后端技术栈关注请求进入系统后如何被认证、校验、编排、持久化、异步化、观测、扩展和恢复。

一个后端请求的完整链路通常是：

客户端请求 -> DNS/CDN/负载均衡 -> API 网关或反向代理 -> 应用服务 -> 鉴权与权限判断 -> 参数校验 -> 业务逻辑 -> 数据库/缓存/外部服务/消息队列 -> 事务或一致性处理 -> 响应序列化 -> 日志、指标、链路追踪 -> 告警与审计。

学习后端技术栈时，最重要的是理解“多用户共享状态”。后端状态一旦写入数据库、缓存、队列或第三方系统，就会引入一致性、回滚、幂等、审计和演进成本。

# 你需要建立的后端能力地图

## 语言与运行时

至少深入掌握一种后端主力语言。常见选择包括 Node.js/TypeScript、Go、Java、Python、Rust 等生态。

需要理解：

- 语言类型系统、异常模型、包管理、模块系统和构建方式。
- 运行时并发模型，例如 Node.js event loop、Java thread pool、Go goroutine、Python async/thread/process。
- 内存管理、垃圾回收、对象生命周期、连接池生命周期。
- 标准库里的网络、文件、时间、加密、序列化和并发工具。
- 应用启动、配置加载、优雅退出、信号处理和资源释放。

Node.js 后端的难点不在语法本身，而在连接池、并发、阻塞操作、进程模型、错误传播和生产环境稳定性。

## HTTP、网络与 API

HTTP 是客户端与服务端协作的基本边界，但后端需要理解得更深。

核心知识：

- HTTP 方法语义：GET、POST、PUT、PATCH、DELETE 的幂等性和缓存含义。
- 状态码：2xx、3xx、4xx、5xx 的责任边界。
- Header、Cookie、CORS、缓存控制、内容协商、压缩和分块传输。
- TLS、证书、HTTPS 终止、反向代理、负载均衡和 keep-alive。
- 超时、重试、限流、熔断、降级、backpressure。
- REST、GraphQL、RPC、gRPC、WebSocket、SSE 的适用边界。
- API 版本化、兼容性、分页、排序、过滤、错误格式和 request id。

优秀 API 设计要回答：

- 资源是什么，动作是什么？
- 哪些字段由客户端传入，哪些字段由服务端生成？
- 请求是否可重试？重复提交会不会造成重复扣款、重复创建、重复发消息？
- 错误能否被客户端明确处理？
- 老客户端升级前会不会被破坏？

## 应用分层与代码组织

后端项目要把入口协议、业务规则、数据访问和外部依赖分开。常见分层：

- Controller/Handler：处理 HTTP/RPC 入参、认证上下文、响应格式。
- Service/Use Case：组织业务流程和事务边界。
- Domain：表达核心业务概念、规则和状态变化。
- Repository/DAO：封装数据库读写。
- Client/Gateway：封装第三方 API、内部服务、消息队列。
- Middleware：横切能力，例如鉴权、日志、限流、trace、错误处理。
- Config：环境变量、密钥、开关和运行参数。

分层不是为了形式，而是为了让业务规则可测试、依赖可替换、接口变更不直接污染数据库代码。

## 数据库与数据建模

数据库是后端深度的核心。必须掌握关系型数据库，尤其是 PostgreSQL 或 MySQL。

基础能力：

- 表、行、列、主键、外键、唯一约束、索引、视图。
- 一对一、一对多、多对多、树结构、枚举状态、软删除。
- SQL 查询、JOIN、聚合、窗口函数、子查询、CTE。
- 索引类型、组合索引、覆盖索引、选择性、执行计划。
- 数据迁移、schema 演进、回滚、兼容发布。
- 备份、恢复、只读副本、主从复制。

建模要点：

- 先表达业务不变量，再考虑查询性能。
- 不要把所有复杂对象无脑塞进 JSON 字段。
- 不要依赖应用层代码替代数据库唯一约束。
- 字段命名、时间字段、状态字段、审计字段要有统一规则。
- 金额、库存、额度等不能用浮点数随意处理。

## 事务与一致性

事务是后端深度的核心之一。你需要理解 ACID：

- Atomicity：一组操作要么都成功，要么都失败。
- Consistency：事务前后业务约束成立。
- Isolation：并发事务之间的可见性和干扰边界。
- Durability：提交后的数据不会轻易丢失。

关键问题：

- 一个业务操作需要改几张表？
- 失败后是否能回滚？
- 并发请求会不会超卖、重复领取、覆盖更新？
- 是否需要乐观锁、悲观锁、唯一约束或事务隔离级别？
- 跨服务操作是否能接受最终一致？

常见模式：

- 单库事务：优先保证核心写入的强一致。
- 幂等键：让重试不会重复产生副作用。
- Outbox：在本地事务里记录待发送事件，再异步投递。
- Saga：把跨服务长事务拆成可补偿步骤。
- 事件最终一致：接受短暂不一致，用消息驱动收敛。

## 缓存

缓存不是“加 Redis 就快了”。缓存引入的是第二份状态，所以必须处理一致性。

需要掌握：

- 本地缓存、分布式缓存、CDN 缓存、数据库缓存的区别。
- cache-aside、write-through、write-back、refresh-ahead。
- TTL、淘汰策略、热点 key、大 key、缓存穿透、击穿、雪崩。
- 缓存 key 设计、版本号、命名空间、序列化格式。
- Redis 数据结构：string、hash、list、set、sorted set、stream、bitmap。
- 分布式锁的适用边界和误用风险。

判断是否要缓存：

- 是否真的被频繁读取？
- 数据是否允许短暂过期？
- 原始查询是否能通过索引或 SQL 优化解决？
- 缓存失效和回源压力能否承受？

## 消息队列与异步任务

队列用于解耦、削峰、重试和异步化，但会带来延迟、重复消费和顺序问题。

常见场景：

- 发邮件、短信、推送。
- 图片、视频、文件处理。
- 订单状态流转后的通知。
- 数据同步、搜索索引更新、埋点处理。
- 高峰写入削峰。

必须理解：

- producer、broker、consumer、topic、queue、partition、offset。
- 至少一次、至多一次、恰好一次的现实边界。
- 重试、死信队列、延迟队列、消费幂等。
- 消息顺序、分区键、重复消息、积压和回放。
- 定时任务、后台 worker 和事件驱动架构的区别。

## 认证、授权与安全

认证回答“你是谁”，授权回答“你能做什么”。

认证方式：

- Session + Cookie。
- JWT。
- OAuth 2.0 / OpenID Connect。
- API Key。
- mTLS 或服务间凭证。

授权模型：

- RBAC：基于角色。
- ABAC：基于属性和上下文。
- ACL：对具体资源授权。
- 多租户隔离：tenant、workspace、organization、project。

后端安全基础：

- 密码哈希与盐，不能明文存储密码。
- SQL 注入、XSS、CSRF、SSRF、命令注入、路径穿越。
- 输入校验与输出编码。
- 文件上传安全、MIME 检查、大小限制、病毒扫描。
- 权限校验必须在服务端完成，不能信任客户端隐藏入口。
- 敏感信息脱敏、审计日志、密钥管理和最小权限。
- 速率限制、验证码、风控、IP/设备维度限制。

## 错误处理与可靠性

后端错误处理不是简单 `try/catch`。要把错误分层：

- 用户输入错误：返回 4xx，可被客户端展示或引导修正。
- 权限错误：401/403，避免泄漏资源存在性。
- 业务冲突：409，例如状态不允许、版本冲突。
- 依赖错误：数据库、缓存、第三方服务超时或失败。
- 系统错误：bug、资源耗尽、配置错误。

可靠性实践：

- 统一错误码和错误响应格式。
- request id / trace id 全链路传递。
- 超时必须显式设置，不能无限等待。
- 重试必须有限制、退避和幂等保护。
- 对外部依赖要有降级策略。
- 关键任务要能恢复、补偿、重放或人工处理。

## 可观测性

生产环境里，能否定位问题比代码是否“看起来正确”更重要。

三大支柱：

- Logs：发生了什么，带上下文和 request id。
- Metrics：系统是否健康，例如 QPS、延迟、错误率、CPU、内存、队列积压。
- Traces：一次请求跨服务经过了哪里，每段耗时多少。

常见指标：

- RED：Rate、Errors、Duration。
- USE：Utilization、Saturation、Errors。
- 数据库慢查询、连接池耗尽、锁等待。
- 缓存命中率、Redis 延迟、内存淘汰。
- 队列 lag、消费失败率、重试次数。

可观测性不是最后加的日志，而是设计 API、任务、事务和依赖调用时就要留下定位线索。

## 测试

后端测试关注业务规则、数据副作用和系统边界。

测试层次：

- 单元测试：纯函数、业务规则、service 逻辑。
- 集成测试：数据库、缓存、队列、外部服务 mock。
- API 测试：请求、响应、认证、错误码。
- 契约测试：客户端与服务端、服务间接口兼容。
- 端到端测试：关键业务链路。
- 迁移测试：schema migration 是否可执行、可回滚、兼容旧代码。

重点测试场景：

- 权限边界。
- 并发写入。
- 重复提交。
- 事务回滚。
- 外部依赖失败。
- 分页和边界条件。
- 金额、时间、时区、精度。

## 部署、环境与运维

后端必须在真实环境中长期运行。

需要理解：

- dev、test、staging、prod 环境差异。
- 环境变量、配置文件、密钥管理。
- Docker 镜像、容器运行、Compose、本地依赖编排。
- CI/CD、构建、测试、发布、回滚。
- 蓝绿发布、滚动发布、灰度发布、feature flag。
- 数据库 migration 和应用发布顺序。
- 进程管理、健康检查、readiness/liveness。
- 日志收集、监控告警、容量规划。

后端发布强调“有状态资源”的兼容性：数据库结构、队列消息格式、缓存 key、老版本服务和新版本服务可能同时存在。

## 文件、对象存储与静态资源

文件处理经常是后端项目的实际复杂点。

需要掌握：

- 本地文件系统与对象存储的差异。
- 上传大小限制、分片上传、断点续传。
- 文件元数据、权限、生命周期、过期链接。
- 图片处理、转码、异步任务。
- 防止路径穿越、恶意文件、超大文件拖垮服务。
- CDN 加速、缓存刷新、私有资源访问控制。

## 搜索、推荐与数据分析入口

多数业务系统最终会需要搜索和分析能力。

基础知识：

- 数据库 LIKE、全文索引和专用搜索引擎的差异。
- 倒排索引、分词、相关性、过滤、排序。
- 搜索索引与主数据库的一致性。
- 埋点、事件表、数据仓库、批处理和实时流。
- OLTP 与 OLAP 的区别。

## 分布式系统基础

不用一开始就追求微服务，但要理解分布式系统的代价。

核心概念：

- 网络不可靠，远程调用一定可能失败或变慢。
- 时间不可靠，跨机器时钟可能偏移。
- 局部失败是常态，一个依赖失败不等于整个系统必须崩溃。
- 数据复制带来延迟和冲突。
- CAP、最终一致、共识、leader/follower、quorum。
- 服务发现、负载均衡、配置中心、网关。

判断是否需要微服务：

- 团队是否足够大，需要独立发布边界？
- 业务域是否清晰？
- 数据边界是否能拆开？
- 是否有足够的 observability、CI/CD 和运维能力？
- 拆分收益是否大于网络、事务、排障和部署复杂度？

多数系统应该先把单体模块化做好，再理解微服务。

# 后端技术栈分层速览

| 层次 | 核心能力 | 关键问题 |
| --- | --- | --- |
| 接入层 | HTTP、网关、负载均衡、TLS、限流 | 请求如何进入系统，如何保护入口？ |
| 应用层 | Controller、Service、Domain、Repository | 业务规则如何组织，边界如何划分？ |
| 数据层 | SQL、索引、事务、迁移、备份 | 状态如何持久化，如何保证一致性？ |
| 加速层 | Redis、本地缓存、CDN | 高频读取如何提速，过期数据如何处理？ |
| 异步层 | 消息队列、任务调度、事件 | 长流程如何解耦、重试和补偿？ |
| 安全层 | 认证、授权、审计、密钥 | 谁能访问什么，风险如何收敛？ |
| 运维层 | CI/CD、容器、配置、发布、回滚 | 服务如何稳定交付和长期运行？ |
| 观测层 | 日志、指标、链路追踪、告警 | 出问题时如何定位和恢复？ |

# 一个实际项目应包含的最小后端闭环

如果要通过项目补齐能力，建议做一个真实但小规模的业务系统，而不是只写 demo CRUD。

功能闭环：

- 用户注册、登录、退出、刷新 token 或 session。
- 角色和权限，例如 admin/member/guest。
- 一个核心资源的 CRUD，例如 project、task、article、order。
- 列表分页、搜索、排序、过滤。
- 文件上传或头像上传。
- 后台异步任务，例如邮件通知或导出任务。
- Redis 缓存一个高频读接口。
- 数据库 migration。
- API 文档和错误码。
- 单元测试、API 测试和少量集成测试。
- Docker Compose 启动应用、数据库和 Redis。
- 日志、request id、基础指标。

生产化检查：

- 所有外部调用有超时。
- 所有写接口考虑重复提交。
- 所有接口有鉴权和权限检查。
- 数据库有必要索引和唯一约束。
- migration 可以在无损发布中执行。
- 密钥不进入代码仓库。
- 日志不泄漏密码、token、身份证、手机号等敏感信息。
- 错误响应不暴露堆栈。

# 学习顺序

## 第一阶段：能独立写可靠 API

目标：从“会写接口”到“接口能被别人放心调用”。

学习内容：

- 一门后端语言和框架。
- HTTP、REST、错误码、分页、参数校验。
- PostgreSQL/MySQL 基础建模和 SQL。
- 认证、授权、密码安全。
- 应用分层、配置、日志。
- 单元测试和 API 测试。

产出标准：

- 能写一个有登录、权限、CRUD、分页、文件上传、测试和 Docker Compose 的服务。
- 能解释每个接口的错误码和权限边界。
- 能通过 SQL 和索引解决常见慢查询。

## 第二阶段：能处理生产复杂度

目标：面对真实流量、失败和变更时不慌。

学习内容：

- 事务、锁、并发、幂等。
- Redis 缓存、缓存失效、热点问题。
- 消息队列、异步任务、重试和死信。
- 可观测性、告警、慢查询、trace。
- CI/CD、灰度、回滚、migration 策略。
- 安全加固和审计。

产出标准：

- 能设计一个不会重复扣款或重复创建资源的写接口。
- 能排查接口变慢是数据库、缓存、下游服务还是应用代码导致。
- 能把一个同步长流程拆成可靠异步任务。

## 第三阶段：能做架构权衡

目标：能够在业务约束下选择合适架构，而不是套模板。

学习内容：

- 模块化单体、微服务、事件驱动、CQRS 的边界。
- 分布式一致性、服务拆分、数据所有权。
- 容量规划、成本、弹性扩缩容。
- 多租户、权限模型、审计合规。
- 技术债治理、架构演进和重构策略。

产出标准：

- 能解释为什么某个系统暂时不该拆微服务。
- 能为一个业务域画出数据模型、接口、异步事件、缓存和部署拓扑。
- 能写出有取舍、有风险、有迁移路径的技术方案。

# 面试与能力自检问题

## API 与协议

- PUT 和 PATCH 的区别是什么？
- 什么时候接口应该返回 400、401、403、404、409、422、500？
- 如何设计分页，offset 和 cursor 各有什么问题？
- 用户重复点击提交按钮，后端如何防止重复创建订单？
- 跨域为什么不能只靠后端 `Access-Control-Allow-Origin: *` 解决所有问题？

## 数据库

- 什么情况下索引不会生效？
- 为什么唯一性必须放到数据库约束里？
- 事务隔离级别解决了哪些并发异常？
- 如何排查一个 SQL 慢？
- 软删除会给唯一约束和查询带来什么问题？

# 常见误区

- 只学框架，不学 HTTP、数据库、事务和部署。
- 把 ORM 当成数据库知识本身。
- 认为 Redis 可以解决所有性能问题。
- 认为微服务天然比单体高级。
- 把 JWT 当成不需要服务端安全设计的万能方案。
- 所有错误都返回 200 或 500。
- 没有唯一约束，靠代码判断“应该不会重复”。
- 没有超时和幂等就做重试。
- 日志没有 request id，出问题只能猜。
- migration 和代码发布不考虑兼容窗口。
